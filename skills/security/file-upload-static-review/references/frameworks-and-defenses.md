# Validation, processing and delivery

Apply an allowlist based on business-required types, informed server-side detection, size and count limits, authorization and rate/resource controls. A single MIME header or filename extension is not proof of file content; signatures and parsers are layers with their own ambiguity and attack surface. Account for double or non-terminal extensions, case changes, trailing dots, path separators, encoding and validation/storage order only when the implementation and platform make them relevant.

Generate server-side names or keys; do not trust the original filename as a path. Store outside executable/public web roots where feasible and expose through an authorized handler or a separately isolated content origin. Determine the actual storage adapter, overwrite rules, upload directory permissions and server handlers rather than assuming an executable PHP extension will run. Configure delivery type and disposition appropriately, set `X-Content-Type-Options: nosniff` where relevant, and assess whether active content can execute in an authenticated application origin.

For Symfony inspect effective `File`/`Image` constraints and request handling, original versus guessed extensions, storage destination and server configuration; none alone proves an executable upload. In Vue or browser JavaScript, type filters and UI checks improve usability but do not enforce server restrictions. For archive extraction, inspect entry paths, symlinks, expanded size and limits. Converters, image decoders, PDF/SVG renderers and scanners can create further trust boundaries; keep their permissions and processing environment explicit.
