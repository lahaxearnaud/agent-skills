# Destination policy and framework boundaries

Prefer fixed configured endpoints or a strict scheme/host/port allowlist when business needs permit it. For arbitrary public destinations, enforce an explicitly defined policy on parsed addresses, including IPv4, IPv6, loopback, link-local, private, multicast and other nonpublic ranges appropriate to the environment. DNS may return multiple addresses or change between validation and connection: verify how the actual client resolves and connects, including proxy resolution. A preflight lookup alone is not proof that the subsequent connection uses the checked address. Deny unsafe redirects or validate each hop under the same policy. Restrict egress independently where possible.

Trace the effective PHP stream context and HTTP client options, cURL protocol and redirect settings, Symfony HttpClient configuration, proxy environment, and library version. For Node servers distinguish built-in fetch/undici, axios and other adapters; defaults and URL resolution can differ by version and configuration. Do not assume a hardcoded base URL cannot be overridden until merge and redirect behavior is established. TrustedHost settings for incoming requests are not automatically outbound controls.

Do not assume a hostname suffix test, substring denylist, IPv4-only regex, metadata header requirement, DNS check, or WAF rule is a complete defense. Credentials, authorization headers and request body can be forwarded depending on client behavior; inspect the exact code and configuration. Reporting a real boundary failure requires the corresponding sink, reachability and guard evidence, not just a bypass idea.
