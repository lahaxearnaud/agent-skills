# Static-analysis patterns and controls

This document turns the published cases into a source-review taxonomy. It is research material for a later skill, not a complete detector specification. The primary sources support the rules below; application-specific reachability still has to be established from the repository.

## What counts as an open redirect

An open redirect exists when externally controlled input can determine a server-generated redirect destination or an automatic browser navigation to an external origin without an effective destination policy. A public link that merely points to another site is not by itself an open redirect. Keep these categories separate:

- **Server redirect:** an HTTP 3xx response with `Location`, generated by PHP `header()`, Symfony `RedirectResponse`, framework redirect helpers, middleware, auth handlers or a proxy/router component.
- **Client-side redirect/navigation:** script assigns a URL to `window.location`/`location.href`, calls `location.assign()`/`replace()`, `window.open()`, or invokes a router API using untrusted data.
- **Off-site URL generation:** a helper generates an external URL, but it becomes an open redirect only if the value reaches a redirect or automatic navigation sink. It may still create an unsafe link or a separate trust problem.
- **Adjacent browser navigation:** HTML meta refresh, a `javascript:` URL, an XSS response, or an external link is related but must be reported under its actual behavior. Do not collapse XSS and open redirect into one class.

HTTP `Location` is a URI reference resolved against the request URI when it is relative, and a 3xx `Location` identifies the preferred target for automatic redirection. A static review therefore needs to inspect both the value and the client/browser interpretation. [RFC 9110 §10.2.2](https://datatracker.ietf.org/doc/html/rfc9110#section-10.2.2)

## High-value source and sink inventory

### Sources to trace

- Query and form values with conventional names such as `next`, `return`, `returnUrl`, `return_to`, `redirect`, `redirect_uri`, `from`, `continue`, `target`, `url`, `destination`, `nextPage`, and framework-specific route values.
- Request headers: `Referer`, `Host`, `Forwarded`, `X-Forwarded-Host`, and `X-Forwarded-Prefix`. These are attacker-influenced unless the framework obtains them from a configured, trusted proxy boundary.
- Values stored in session, cookies, flash state, database fields, OAuth `state`, callback parameters, or saved form state. Trace write and later read; a redirect flow may span requests or authentication.
- Client state: `location.search`, `location.hash`, `document.referrer`, `URLSearchParams`, route query/params, `postMessage`, storage, and API-provided `returnTo` values.

### Sinks to enumerate

- PHP: `header('Location: ...')`, Symfony `RedirectResponse`, controller `redirect()` helpers, and response objects whose `Location` header is set directly.
- Java/JVM: servlet `sendRedirect`, Spring `redirect:` view names, controller/framework redirect helpers, login success/failure handlers, and configurable server valves.
- JavaScript: assignment to `window.location` or `location.href`, `location.assign()`/`replace()`, `window.open()`, `window.navigation.navigate()`, and automatic meta refresh.
- Vue/Nuxt: `router.push()`/`replace()`, `navigateTo()`, `reloadNuxtApp({ path })`, route guards returning destinations, and `<router-link>`/`<NuxtLink>` when the destination is computed from untrusted data.
- Other SPA frameworks represented in the corpus: React Router `redirect()`, `<Link>`, `useNavigate()`, loader/action return values; Qwik redirect helpers; Next.js `redirects()`/`rewrites()`.

Framework helpers are sinks, not sanitizers. Symfony documents `RedirectResponse` as a way to send the client to a URL, and PHP documents `header('Location: ...')` as a browser redirect. Vue Router documents `router.push()` and link components as navigation APIs. [Symfony HttpFoundation](https://symfony.com/doc/current/components/http_foundation.html), [PHP `header()`](https://www.php.net/manual/en/function.header.php), [Vue Router navigation](https://router.vuejs.org/guide/essentials/navigation)

## Recurring patterns from the 60 cases

### 1. Unvalidated post-login or post-action destination

Look for a login handler that reads `next`/`returnUrl` then redirects after authentication, logout, account confirmation, save, locale/currency switch, or a form callback. Cases include CakePHP, WeGIA, Jupyter, Jenkins, Redash, Snipe-IT, Umbraco and Sylius. Record the exact auth/feature precondition and whether the target is stored for later use.

**Common design flaw:** a URL is treated as “return location” business state but is stored/forwarded as an arbitrary serialized URL. Prefer an internal route identifier or a small enum mapped to fixed route names. If the product must accept URLs, validate once at the trust boundary and redirect only to the canonical result.

### 2. Host and referrer trust

Search use of request `Host`, `Referer`, or forwarded headers in absolute-URL generation and redirects. Sylius and AdonisJS trust `Referer`; Flask-AppBuilder demonstrates Host-derived redirects; Angular SSR shows proxy-prefix influence. Snipe-IT demonstrates delayed session persistence.

Treat headers as untrusted at application boundaries. Use framework trusted-proxy configuration and explicit allowed hosts; do not accept user-supplied `X-Forwarded-*` values from arbitrary clients. A static code review may not prove how ingress overwrites headers, so report the deployment condition as unknown until configuration is inspected.

### 3. Parser differential and check/use mismatch

Repeated `parse_url`, regex, `startsWith`, local-only helpers, or “remove scheme and host” checks can disagree with the browser or the redirect library. Cases include Symfony CVE-2024-50345, Spring CVE-2024-22243/22259, Express CVE-2024-29041, TYPO3, mod_auth_openidc, Flask-Security, WebOb, and Redash.

For same-origin redirects, resolve with a parser whose semantics match the final consumer, then compare the parsed **origin** (scheme, host, effective port) to a fixed expected origin. Emit a canonical relative path or select a fixed internal route after the check. Do not validate a raw string and later decode, normalize, concatenate, prepend a base URL, or parse it with a different implementation.

Look specifically for transformations before and after validation: percent decoding, Unicode/IDNA handling, trimming control characters or whitespace, slash/backslash rewriting, dot-segment removal, path joining, URL joining, origin concatenation, and header/session serialization. WHATWG URL parsing rules are the browser-facing reference; syntax accepted by a server parser is not sufficient proof that the browser will stay on-origin. [WHATWG URL Standard](https://url.spec.whatwg.org/)

### 4. Protocol-relative destinations and slash normalization

Destinations beginning with `//` inherit the current scheme but select another authority. Browser or framework normalization may turn backslashes, extra slashes, encoded slashes, or dot segments into that form after an earlier check. See Symfony Routing, Vue Router issue #3946, React Router, Angular SSR, Nuxt, Qwik, WebOb, Redash, and Mastodon.

Static review should follow the *normalized* destination, not just the raw value at the guard. Determine whether the consumer parses a path relative to the current origin or interprets it as a scheme-relative URL. Avoid “only starts with `/`” and “remove all leading slash pairs” as sole policies; prove the result remains a path on the intended origin after the same normalization the sink performs.

### 5. Framework-specific implicit redirects

Some redirect behavior is created by configuration or framework defaults instead of an obvious controller call: Spring's catch-all view mapping and `redirect:` prefix, Tomcat FORM authentication/default-servlet behavior, Next.js configured redirects/rewrites, and Qwik slash-fixing middleware. Review route files, server adapters, auth configuration, and deployment settings alongside code.

### 6. OAuth and identity-provider flows

Trace the whole flow: request parameter → client lookup → registered redirect URI validation → state/session → consent/error branch → callback → final redirect. Validation must occur before every branch that can return a redirect, including unsupported response types, denial/error pages, logout, and callback overrides. Validate that state is integrity-protected and bound to the initiated flow; base64 encoding does not provide integrity.

For OAuth authorization servers, RFC 9700 says registered redirection URIs must be compared by exact string matching (with the stated loopback-port exception for native apps) and says clients and authorization servers must not expose query-parameter-driven open redirectors. Do not substitute host suffix checks or wildcards for that requirement. [RFC 9700 §2.1 and §4.11](https://datatracker.ietf.org/doc/html/rfc9700), [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749)

## CSP and impact limits

Do not treat CSP as a general open-redirect fix. The CSP Level 3 working draft consulted for this corpus does not define a general `navigate-to` directive. `form-action` constrains form submissions, while `frame-ancestors` controls which origins may embed a response. `default-src` is a fallback for fetch directives, not a universal restriction on top-level navigation. A strict `script-src` can reduce some script-execution outcomes (including some unsafe script-scheme cases), but it does not make an ordinary redirect to an attacker-controlled HTTPS page safe. [CSP Level 3 working draft, 2026-10-27](https://www.w3.org/TR/2026/WD-CSP3-20261027/), [MDN `default-src`](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/default-src), [MDN navigation directives](https://developer.mozilla.org/en-US/docs/Glossary/Navigation_directive)

An open redirect's baseline impact is often phishing and abuse of a trusted domain. Higher impact requires evidence of a chain: OAuth code/token delivery, account takeover, sensitive state in the URL, a privileged post-auth context, or another trust boundary. Do not infer session-cookie theft merely because a browser leaves the site; ordinary same-origin policy prevents a destination site from reading the source site's cookies. Attribute any stronger impact to the source and state its prerequisites.

## Static review procedure to derive into the skill

1. **Map behavior:** identify server routes, controllers, auth callbacks, login/logout handlers, framework redirect configuration, SSR adapters, Vue/router guards, and client navigation utilities.
2. **Enumerate sinks:** search for `Location`, redirect helpers, `sendRedirect`, JS location APIs, router navigation APIs, and HTML meta refresh. Include wrappers and user-defined helpers.
3. **Trace sources:** follow request params/headers, route state, OAuth fields, persisted session/database values, storage, URL query/hash, referrer, and API data.
4. **Follow transformations:** document parse/decode/normalize/concatenate/store/retrieve operations in order. A guard before a later mutation is not an effective guard.
5. **Prove destination policy:** identify whether there is an explicit fixed-route map or exact-origin/registered-URI allowlist, and whether the sink uses the checked canonical value.
6. **Check conditions:** record dependency version, route/feature configuration, auth role, trusted-proxy assumptions, SSR/client mode, user interaction, and fallback branches. Mark unstated conditions unknown.
7. **Separate findings:** distinguish direct server redirect, client navigation, off-site URL generation requiring a sink, OAuth redirect URI misvalidation, SSRF, meta refresh, and XSS.
8. **State impact proportionally:** describe the minimum demonstrated consequence and any conditional chain. Do not assign severity from the CVSS score or advisory title alone.

## Primary standards and documentation

- [OWASP Unvalidated Redirects and Forwards Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Unvalidated_Redirects_and_Forwards_Cheat_Sheet.html) — recommends allowlisting and explains phishing/forward risks.

- [RFC 9110 §10.2.2](https://datatracker.ietf.org/doc/html/rfc9110#section-10.2.2) — semantics of `Location` and relative references.
- [WHATWG URL Standard](https://url.spec.whatwg.org/) — browser URL parsing and normalization.
- [RFC 9700](https://datatracker.ietf.org/doc/html/rfc9700) and [RFC 6749](https://datatracker.ietf.org/doc/html/rfc6749) — OAuth redirect URI validation and open redirectors.
- [Symfony HttpFoundation](https://symfony.com/doc/current/components/http_foundation.html) and [PHP `header()`](https://www.php.net/manual/en/function.header.php) — server redirect sinks.
- [MDN `Location.assign()`](https://developer.mozilla.org/en-US/docs/Web/API/Location/assign), [MDN `Window.location`](https://developer.mozilla.org/en-US/docs/Web/API/Window/location), and [Vue Router navigation](https://router.vuejs.org/guide/essentials/navigation) — client navigation sinks.
