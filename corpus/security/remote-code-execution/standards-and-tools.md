# Standards, secure APIs, and static-analysis references

This inventory records documented capabilities and limits; it does not claim that a scanner was run against a target. Consulted online sources and current version context are recorded here. Installed-skill operational guidance later paraphrases its external references locally.

## Weakness and review taxonomies

| Source | Relevant scope | Use and limit |
| --- | --- | --- |
| [CWE-78: OS Command Injection](https://cwe.mitre.org/data/definitions/78.html) | Improper neutralization of special elements in OS commands. | Useful label for shell-command alteration and impact categories. Do not apply it automatically to every `exec` call or to argument injection without checking the actual command parser. |
| [CWE-88: Argument Injection or Modification](https://cwe.mitre.org/data/definitions/88.html) | Unintended argument/option interpretation. | Keeps direct argument-vector risks distinct from shell metacharacter injection. A called program can interpret a value as an option or secondary language. |
| [CWE-94: Code Injection](https://cwe.mitre.org/data/definitions/94.html) | Improper control of generated/executed code. | Applies when untrusted data changes executable code or an interpreter expression. A code-evaluation API with a constant expression does not alone satisfy the data-flow condition. |
| [CWE-502: Deserialization of Untrusted Data](https://cwe.mitre.org/data/definitions/502.html) | Untrusted object reconstruction. | A candidate weakness, not proof of RCE: confirm remote reachability, object behavior/gadget, dependency set and impact. |
| [OWASP Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Injection_Prevention_Cheat_Sheet.html) and [OS Command Injection Defense](https://cheatsheetseries.owasp.org/cheatsheets/OS_Command_Injection_Defense_Cheat_Sheet.html) | Interpreter boundaries and prevention. | Prefer APIs that preserve code/data separation; validate to the domain, and use context-specific escaping only when no structured API is available. OWASP distinguishes OS command injection from argument injection. |
| [OWASP SSTI Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Template_Injection_Prevention_Cheat_Sheet.html) | Server-side template-source injection. | Use to distinguish template source from values rendered by a trusted template and to review sandboxing. It is not a substitute for inspecting engine extensions and application reachability. |

## API and framework documentation

| Source | Documented behavior | Review use and caveat |
| --- | --- | --- |
| [Python `subprocess`](https://docs.python.org/3/library/subprocess.html) | Does not implicitly choose a shell; explicitly setting `shell=True` makes the caller responsible for quoting. The docs also note Windows batch-file argument behavior. | Inspect the exact `shell`, executable, argv and platform. No shell does not prevent the invoked program from treating an argument as an option or script. |
| [Node.js `child_process`](https://nodejs.org/api/child_process.html) | APIs vary in whether they use a shell; shell-enabled calls must not receive unsanitized input. | Trace `exec`, `execSync`, `spawn`/`execFile` options and version. Argument arrays help only when shell mode is absent and the target program's arguments are safe. |
| [Symfony Process](https://symfony.com/doc/current/components/process.html) | Recommends an array of arguments; string shell commands require caller-managed platform-specific escaping. | For PHP/Symfony, distinguish `new Process([...])` from `Process::fromShellCommandline(...)`; inspect component version and the actual platform. |
| [Java `ProcessBuilder`](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/lang/ProcessBuilder.html) | Starts the executable and arguments represented by its command list. | Treat executable, argv, environment and working directory as separate controls. `ProcessBuilder` is not a general shell by itself, but wrappers or child programs may interpret arguments. |
| [PHP `unserialize`](https://www.php.net/manual/en/function.unserialize.php) | Warns not to pass untrusted input even with `allowed_classes`; reconstruction can load/execute code through object instantiation and autoloading. | Strong candidate signal; still prove the remotely controlled input and target-version behavior. Prefer JSON for data interchange. |
| [Java `ObjectInputFilter`](https://docs.oracle.com/en/java/javase/26/docs/api/java.base/java/io/ObjectInputFilter.html) | Provides class and graph/resource checks during native deserialization; the docs warn untrusted deserialization is inherently dangerous. | Verify a filter is installed and actually applied to every stream. Allowlisting and resource limits need to match the use case. |
| [Python `pickle`](https://docs.python.org/3/library/pickle.html) | Explicitly warns that crafted pickle data can execute code and says not to unpickle untrusted/tampered data. | Strong risk signal; confirm input origin and entry point. A signed object is only trustworthy if the signing key and complete verification path are trusted. |
| [Twig sandbox](https://twig.symfony.com/doc/3.x/sandbox.html) | Untrusted Twig templates need a sandbox policy; a dedicated environment and explicit allowed tags, filters, functions, methods and properties are described. | Check deployed Twig version, the environment used for untrusted templates and registered extensions. Ordinary output escaping does not constrain template execution. |
| [Jinja sandbox](https://jinja.palletsprojects.com/en/stable/sandbox/) | Provides a sandboxed environment and customizable access restrictions for untrusted template rendering. | A sandbox is a capability boundary to review, not a blanket guarantee; inspect exposed objects, custom filters and exact version. |
| [Node.js `vm`](https://nodejs.org/api/vm.html) | Explicitly states that the module is not a security mechanism and must not be used to run untrusted code. | Do not credit a separate VM context as a sandbox. Verify whether the input is code and whether it reaches `runIn*`/compile APIs. |

## Static analyzers and documented query behavior

| Tool and source | Documented rule model | Coverage limits for this review |
| --- | --- | --- |
| [CodeQL Python command-line injection](https://codeql.github.com/codeql-query-help/python/py-command-line-injection/) (`py/command-line-injection`) | Path query for untrusted data reaching command execution; docs show selecting fixed commands from an allowlist. | Query behavior is language/library-specific. Review option injection, custom wrappers, hidden configuration and async/job paths manually. Documentation is not a scan result. |
| [CodeQL Python code injection](https://codeql.github.com/codeql-query-help/python/py-code-injection/) (`py/code-injection`) | Path query for input flowing into dynamic code evaluation. | Cannot establish product-level route/reachability or all runtime interpreter bindings solely from a sink label; inspect the path and context. |
| [CodeQL Java command-line injection](https://codeql.github.com/codeql-query-help/java/java-command-line-injection/) (`java/command-line-injection`) | Query for user input to command execution. | A process API alone is not shell injection; check whether the API starts a shell or whether the called program interprets the arguments. |
| [CodeQL JavaScript direct/second-order/indirect command injection](https://codeql.github.com/codeql-query-help/javascript/js-command-line-injection/), [second-order](https://codeql.github.com/codeql-query-help/javascript/js-second-order-command-line-injection/), [indirect](https://codeql.github.com/codeql-query-help/javascript/js-indirect-command-line-injection/) | Separate query help documents direct command construction, option/argument effects, and wrapper paths. | A useful model for stored data and secondary programs; the reviewer must establish actual application triggers and tool behavior. |
| [CodeQL path queries](https://codeql.github.com/docs/writing-codeql-queries/creating-path-queries/) and [data-flow overview](https://codeql.github.com/docs/writing-codeql-queries/about-data-flow-analysis/) | Path queries report source-to-sink paths; dataflow analysis depends on modeled sources, sinks, barriers and available code. | Official docs note analysis tradeoffs and that flow through unavailable library source may not be computable. Missing findings do not prove safety; findings require contextual validation. |
| [Semgrep taint rules](https://semgrep.dev/docs/writing-rules/rule-ideas) and [taint glossary](https://semgrep.dev/docs/writing-rules/glossary) | Rules identify sources, propagators, sanitizers and sinks; Semgrep documents intra-procedural and cross-file distinctions. | Coverage depends on rule edition/version/language and user rule models. A sanitizer may be modeled too broadly/narrowly; inspect scope and path. Documentation is not a target scan. |

No target scanner or static analyzer was run for this corpus. These pages were consulted as documentation on 2026-11-03; product capabilities and current-version details can change. Confirm the edition, language, query pack and version before using a tool's output as evidence.
